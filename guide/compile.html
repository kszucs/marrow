Compiling a query to a native executable

marrow compile — the AOT lane, exposed to users

Everything else in this guide runs through the Python bindings: build a plan, call .collect(), get a RecordBatch back, in the same process that built the plan. marrow compile is a different thing: it turns a Mojo source file into a native executable that runs the query later, from the command line, without Python. The executable loads the Mojo runtime libraries; --bundle (below) copies them next to it, so the machine that runs it needs no marrow or Mojo install.

Note

The code on this page is Mojo, compiled ahead of time — not the Python marrow.expr API the rest of this guide uses. See Expression execution for the lazy Python frontend.

When to reach for this instead of the lazy frontend

The query shape — which relation nodes, in what order, over which columns — is frozen at compile time. Only scalars and paths are late-bound. That is the whole trade:

  • A fixed report that runs against a different file and a different threshold every day — marrow compile fits well. Ship one binary, run it with different --flag values; with --bundle, the target machine needs no marrow install.
  • A query whose shape varies — a different filter, a different set of group-by keys, an ad hoc notebook session — wants the Python lazy frontend instead. Reshaping a plan there is a line of Python; reshaping a compiled binary is a rebuild.

State the cost up front, because it will not announce itself: a marrow compile build takes roughly 1-2 minutes per invocation, because mojo build elaborates the whole of marrow at -O3 for every compile — there is no incremental build. That is fine for a binary you build once and run many times; it is a bad fit for an edit-compile-run loop.

What you write

A query file is an ordinary Mojo program with a main(). It declares its command-line surface, parses it, builds a plan, and runs it:

benchmarks/binary_size/query_cli.mojo
"""The AOT lane's product surface, end to end — and the gate that keeps it cheap.

This is what a user of `marrow compile` actually writes: a fused plan over a
known schema, a late-bound threshold, a late-bound input path, and `cli.run()`.
Compiled it is a standalone `SELECT` over a Parquet file with `--help`,
`--describe`, `-o` and `--format`:

    marrow compile benchmarks/binary_size/query_cli.mojo -o orders
    ./orders orders.parquet --min-amount 250
    ./orders orders.parquet --format csv | head

Every expression here is comptime — `col("amount", int64)` is a
`NumericColumn[Int64Type]`, the predicate fuses into one SIMD loop — so the gate's job
is to show that wrapping a plan in a command-line surface does **not** drag the
runtime interpreter in behind it. `marrow::expr::runtime` must link 0 symbols:

    pixi run binary_size query_cli query_scan

`run()` is called without `[parquet=True]` / `[ipc=True]`, so the Parquet and
Arrow IPC *writers* are gated out and this binary prints or writes text. That
is the default on purpose: the writers are the largest thing the CLI layer can
pull in, and a query that pipes its result should not pay for them.

**The plan names no rules, so this binary links no optimizer** — the same
default `execute()` has. An earlier draft had `run` apply `ScanPruning` itself,
and that single call measured 1,467,352 bytes (+33% of this gate):
`Optimizer.run` walks the plan through `DynRelation._dispatch`, whose ten arms
each rebuild their node and so register `_to_operator_tramp[X]`, linking every
physical operator and its kernels into a binary whose plan names two node
types. Adding `.optimize[ScanPruning]()` here is what it costs to make an AOT
binary prune; no gate pays it today, so the figure is recorded rather than
gated.
"""

from marrow.dtypes import field, int64, string
from marrow.expr import QueryCli, col, scan
from marrow.schema import schema


def main() raises:
    var cli = QueryCli(
        String("orders"),
        description=String("Orders at or above a minimum amount."),
    )
    var min_amount = cli.param(
        String("min-amount"),
        int64,
        default=Int64(0),
        help=String("keep orders whose amount is at least this"),
    )
    cli.argument(String("src"), help=String("input Parquet file"))

    if cli.parse():
        var sch = schema(
            [
                field("id", int64),
                field("amount", int64),
                field("name", string),
            ]
        )
        cli.run(
            scan(cli.get(String("src")), sch^).filter(
                col("amount", int64) >= min_amount
            )
        )

Four calls carry the whole surface:

  • QueryCli(prog, description=...) — the program’s name and its --help blurb.
  • cli.param(name, dtype, default=..., help=...) — a late-bound scalar. It returns the plan node and declares the option, which is the point: one line produces --min-amount, its --help entry, the string-to-int64 coercion and the NumericParam[Int64Type] the predicate is built from, so the parser and the plan cannot drift apart. Required unless it has a default.
  • cli.argument(name, help=...) — a positional, read back with cli.get(name). Paths are the usual case.
  • cli.run(plan) — execute and write the result.

cli.option(...) and cli.flag(...) are there too, for a string or boolean the plan does not consume as a scalar.

param() — the late-bound value

cli.param(name, dtype) returns a node structurally identical to lit(value), except the scalar behind it arrives from the command line. It composes with everything a literal does — comparisons, arithmetic — and costs nothing extra per row: the value is resolved once per batch, not once per element.

A plan is immutable and stateless, so the value does not live in the node. It travels through the execution as a Bindings map, which cli.run() assembles from the parsed arguments. Two executions of the same plan with different values cannot interfere.

param() is also available directly, without a QueryCli — param("min-a", int64, default=0) — for a plan that binds its own values through plan.execute(bindings=...). It is numeric-only today; there is no string or temporal parameter, so a late-bound path is an ordinary cli.argument()/cli.option() string rather than a node.

What the compiled binary does

Every QueryCli binary gets five arguments without the author declaring them: -h/--help, --describe, -o/--output, --format and --max-rows.

$ ./orders --help
usage: orders [-h] [--describe] [--output PATH] [--format FMT] [--max-rows N] [--min-amount N] <src>

Orders at or above a minimum amount.

options:
  -h, --help          show this help message
      --describe      print the query plan and exit
  -o, --output PATH   write results here (default: stdout)
      --format FMT    output format: table | csv | parquet | ipc (default: inferred from --output's extension, else table)
      --max-rows N    rows to print for `table` output, 0 for all (default: 20)
      --min-amount N  keep orders whose amount is at least this (default: 0)

arguments:
  src                 input Parquet file (required)

Running it against a seven-row Parquet file whose amount column is [100, 250, 90, 1000, 250, null, 42]:

$ ./orders orders.parquet --min-amount 250
id  amount  name
--  ------  ----
2   250     bob
4   1000    dave
5   250     erin
(3 rows)

--describe prints the plan and exits, which is the only way to ask a shipped binary what query is baked into it. It short-circuits the required-argument check, so it needs no input file:

$ ./orders --describe
Filter(ParquetScan(), greater_equal(col(amount), param(min-amount)))

Output formats

The default is an aligned text table, capped at --max-rows (20) with a footer that says so — print(batch) alone prints RecordBatch(num_rows=3, schema=...) and no data, which is fine as a repr and useless as a report. --format csv writes RFC 4180 CSV and is never truncated, because a silently capped pipe is a data-loss bug:

$ ./orders orders.parquet --format csv
id,amount,name
1,100,alice
2,250,bob
3,90,carol
4,1000,dave
5,250,erin
7,42,grace

-o PATH writes to a file instead of stdout and picks the format from the extension — .csv for CSV, .parquet for Parquet, .arrow/.ipc for Arrow IPC, anything else CSV. --format overrides the guess.

Parquet and Arrow IPC are opt-in at compile time. They are the largest thing this layer can pull into a binary, and a query that prints or pipes its result should not carry them, so run() takes them as comptime parameters:

cli.run(plan)                  # text only — table and csv
cli.run[parquet=True](plan)    # + the Parquet writer
cli.run[ipc=True](plan)        # + the Arrow IPC writer

A binary built without one says so, and names the fix, rather than failing obscurely:

$ ./orders orders.parquet -o out.parquet
orders: error: --format parquet: this binary was built without the Parquet writer; build it with `cli.run[parquet=True](plan)`

This replaces the old -D MARROW_CLI_WRITERS=true build flag. Putting the choice in the source means the query file states which formats its binary supports, and no build invocation can disagree with it.

When this was measured on the query_cli program, linking both writers (cli.run[parquet=True, ipc=True](plan)) added about 657 KB of __text to the text-only build. The text-only build is the one the CI size gate tracks; its current figure is in benchmarks/binary_size/baseline.json.

nm -C on the two: marrow::parquet::writer is 0 symbols in the first and 7 in the second, and marrow::expr::runtime is 0 in both.

Errors

A usage error prints the usage line and exits 2; an execution error exits 1. Neither surfaces a Mojo traceback:

$ ./orders --min-amont 5 orders.parquet
usage: orders [-h] [--describe] [--output PATH] [--format FMT] [--max-rows N] [--min-amount N] <src>
orders: error: unrecognized option '--min-amont'

$ ./orders --min-amount abc orders.parquet
orders: error: --min-amount expects an integer, got 'abc'

Column names are checked against the schema, not the compiler

col("amount", int64) fixes the column’s dtype at compile time — that is what makes the predicate fuse — but the name is resolved against the schema when the plan is built, so a typo is a run-time error naming the column, not a compile error — marrow/schema.mojo’s field(name=...) raises Field with name `amont` not found., which run() reports as orders: error: Field with name \amont` not found.`.

It could be a compile error, and that is the obvious next step for this surface. marrow/expr/comptime/tests/test_schema_handle.mojo pins the four compiler contracts it needs — a struct with heap-allocated fields is a valid comptime parameter, __getattr_param__ fires for a missing attribute, its return type may depend on the attribute name and still satisfy NumericColumn’s NumericType bound, and comptime assert turns an unknown name into a build failure carrying its own message. With a schema as a comptime parameter, t.amount resolves to NumericColumn[Float64Type] and t.amont fails the build with constraint failed: unknown column: amont.

What does not exist yet is the production side of it: the handle and the comptime schema in that file are defined in the test, and nothing derives one from a Parquet footer at build time. Until that lands, col(name, dtype) is the working spelling and a bad name is caught when the plan is built.

marrow compile — building the binary

Installing marrow with the compile extra (pip install marrow[compile]) registers a marrow console script backed by python/marrow/compile.py. compile is a subcommand of it, so more subcommands can join it later:

$ marrow compile benchmarks/binary_size/query_cli.mojo -o orders

Inside a checkout, the equivalent without the wrapper is the recipe marrow compile runs for you:

$ pixi run -e dev mojo build -O3 -g0 -I . benchmarks/binary_size/query_cli.mojo -o orders
WarningThe compile extra does not resolve on PyPI today

The extra pins mojo>=1.1,<2, and marrow needs a nightly Mojo build; PyPI’s stable mojo package tops out at 1.0.0, so pip install marrow[compile] cannot satisfy it from PyPI alone. Install the nightly explicitly first — pip install --pre mojo-compiler --extra-index-url https://whl.modular.com/nightly/simple/ — or work inside marrow’s own pixi environment, which already has the pinned nightly. check_mojo_version reports the same thing at run time if the stable wheel is what got installed.

marrow resolves the mojo compiler on PATH (raising a named error, including the nightly-vs-stable-PyPI distinction, if it is missing or out of range) and the marrow/ Mojo package to pass as mojo build’s -I — via --marrow-path, the MARROW_MOJO_PATH environment variable, the copy bundled into the wheel, or by walking up from the current directory looking for a marrow/ + pixi.toml pair, in that order. Then it runs mojo build -O3 -g0 -I <marrow> <src> -o <out> followed by strip, so a compiled query’s size is directly comparable to the numbers in benchmarks/binary_size/.

Useful flags:

  • -o OUTPUT (or the positional form, marrow compile query.mojo out) — where to write the binary. Defaults to the source file’s name without .mojo, in the current directory.
  • --fast — build with -O1 instead of -O3: a faster compile, a slower binary. Still on the order of a minute, since elaborating marrow dominates either way.
  • --bundle DIR — see below.
  • --marrow-path, -v, --no-strip — override package resolution, print the underlying mojo build command, or skip stripping debug symbols.

--bundle — a relocatable, self-contained directory

A compiled binary still dynamically links a handful of Mojo/MAX runtime .dylib/.so files, resolved through the local pixi environment’s rpath — copying the bare binary to another machine will not run there. marrow compile query.mojo -o query --bundle DIR copies the binary plus the transitive closure of its non-system shared-library dependencies into DIR and rewrites the rpath to @loader_path (macOS) / $ORIGIN (Linux), so DIR runs standalone — no pixi environment, no marrow install:

$ marrow compile query.mojo -o query --bundle ./dist
$ ./dist/query data.parquet --min-amount 5

The closure walks otool -L / ldd recursively rather than hardcoding a dylib list, because the set is not fixed — a -D MARROW_GPU=true build pulls in an additional GPU runtime library that a CPU-only build does not link.

The bundle also includes marrow’s Parquet compression codecs — zstd, snappy, lz4, zlib and brotli. Those are dlopen-ed at runtime rather than linked (see marrow/utils/compression.mojo), so they are invisible to otool -L/ldd and need their own step: --bundle resolves the active pixi/conda environment’s lib/ directory ($CONDA_PREFIX, or two directories up from mojo on PATH — never a hardcoded pixi path) and copies whichever of the five it finds there, plus their own transitive dependencies (libbrotlienc/libbrotlidec each pull in libbrotlicommon). A codec that is not installed is skipped with a warning rather than failing the bundle. This matters because snappy is pyarrow’s default Parquet compression — without it, the bundle could only read uncompressed files. compression.mojo tries an executable-relative path before the bare soname it otherwise dlopens, which is what makes the staged copy actually get found at runtime; copying alone is not enough, since a bare dlopen("libsnappy.dylib") never searches @loader_path.

Zipping the bundle: use zip -ry, not zip -r. A plain zip -r dereferences symlinks, turning each deduplicated alias back into a full copy of the same bytes. zip -ry DIR.zip DIR (the -y stores symlinks as symlinks) preserves the dedup; unzip on a machine of the same OS/arch to get the directory back exactly as built.

What “self-contained” has and has not been verified to mean. The bundle’s own binary has its rpath rewritten to @loader_path, and that path has been verified end to end: a snappy-compressed Parquet file reads correctly from a freshly built bundle run with no DYLD_LIBRARY_PATH or CONDA_PREFIX set, from a different working directory, via both a relative (./query) and an absolute-path invocation. What is not rewritten is the codec libraries’ own @rpath entries — bundle() only rewrites the main binary’s rpath. In practice that means a codec with its own dependency (libbrotlienc depends on libbrotlicommon) resolves it via the codec library’s rpath as recorded on the build machine, which is not verified to carry over elsewhere. This mirrors the existing behaviour for the runtime-dylib closure, so it is not a new gap — full cross-machine portability of every codec remains an open question, not a claim this page makes.

Static linking is not on the table on macOS — there is no libSystem.a to link against. It may be possible on Linux; that is untested here.

Why this is small

The point of the AOT lane is that the binary contains little beyond the query. col("amount", int64) is a NumericColumn[Int64Type], so the predicate’s structure lives in its type and fuses into one SIMD loop; no interpreter is reachable, and the kernels the query does not name are never linked. Anything that scans Parquet does also link the storage layer, including about 50 KB for the OpenDAL backend.

The command-line surface preserves that. Parameter coercion is monomorphic — cli.param("min-amount", int64) instantiates one coercion function for int64 and stores it behind a thin function pointer, rather than dispatching on a runtime dtype and dragging in all eleven numeric widths — and the file writers are behind the comptime gate described above. The benchmarks/binary_size/query_cli gate exists to keep it that way, and measures marrow::expr::runtime at 0 symbols.
