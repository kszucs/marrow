# Golden query corpus — design

**Status:** design, not started. **Date:** 2026-08-19.

## Goal

Establish that marrow's query engine returns **correct results for the queries
it supports**, and make "the queries it supports" a machine-checked artifact
rather than prose.

Both halves matter. `docs/backlog.md` records what is *missing* — 8 relation
nodes, no `Distinct`/`Union`, no subquery node, windows AOT-only — but nothing
in the tree states what works. A golden corpus is that statement, and it is
checked on every run.

## Non-goals

- **Not a fuzzer.** Randomized query generation, metamorphic oracles and
  shrinking are deliberately deferred; see "Rejected and deferred".
- **Not a SQL frontend.** No runtime SQL support is added. The one-time
  corpus transpile (see "Seeding from the SQLite corpus") is an offline script
  whose *output* is committed; it is not a component of the suite.
- **Not scan or format coverage.** Every case reads an **in-memory** source, so
  what is under test is the engine, not Parquet decode, row-group pruning or
  IPC. Those keep their own suites (`marrow/parquet/tests/`, `marrow/tests/`).

## What exists today

| asset | what it covers | limit |
|---|---|---|
| `python/marrow/tests/test_clickbench.py` | 43 ClickBench queries vs a DuckDB reference, real `hits` parquet | one dataset, one query shape, wide non-null data; each case subprocessed because of open memory-safety defects |
| `marrow/expr/tests/` (~230 KB) | hand-written expression, plan, aggregate, join, pushdown, streaming cases | no shared notion of a *query* with an expected result |
| `marrow/expr/tests/test_parity.mojo` | AOT vs runtime lane, four hand-picked axes | expression level only, never whole queries |
| archery integration (14/14) | IPC and C-Data conformance | format, not query semantics |

Nothing checks the two lanes against a common expectation at query level, and
nothing enumerates the supported surface.

## Decision

**A ClickHouse-stateless-shaped golden corpus of marrow queries, with
expectations generated by DuckDB, run through both lanes and under multiple
execution configurations.**

Four reference engines were surveyed (`~/Workspace/{duckdb,datafusion,polars,ClickHouse}`).
Every one of them makes a hand-written corpus the backbone and adds
path-coverage on top; none makes randomized generation the primary mechanism.

- **ClickHouse** — `tests/queries/0_stateless/`: 9,949 `.sql` paired with 13,291
  `.reference` files, re-run under a `SettingsRandomizer` that randomizes **187
  settings** per run.
- **polars** — hand-written tests plus hypothesis over *data* (63 files, 177
  `@given`), and CI re-runs the whole suite under `POLARS_AUTO_NEW_STREAMING=1`
  with one matrix leg pinned to `POLARS_IDEAL_MORSEL_SIZE=4` against 100,000
  everywhere else.
- **DuckDB** — 4,399 `.test` files plus `DebugStatementVerification`
  (copied / reparsed / serialized / prepared / unoptimized), all requiring
  identical results.
- **DataFusion** — 500 `.slt` files plus 15 fuzzers.

## Rejected and deferred

**Importing a foreign `.slt` corpus as a live suite — rejected.** (Mining one
offline for queries is a different thing, and is adopted; see "Seeding from the
SQLite corpus".)

1. Running it needs a SQL frontend *at test time*, which marrow does not have.
2. Coverage is thin: a coarse screen of DataFusion's corpus for constructs
   marrow's IR cannot express (`arrow_cast`/`arrow_typeof`/`make_array` 22%,
   struct/list access 13%, `EXPLAIN` 12%, subqueries 10%, regex/temporal 6%,
   windows 5%, `DISTINCT` 3%) leaves ~45% before type-coercion triage, and 460
   statements are `CREATE EXTERNAL TABLE ... STORED AS CSV`.
3. The result model **discards type fidelity on purpose** — `query IIR` type
   letters coerce results before comparing, and results above `hash-threshold`
   are stored as an MD5 of rendered text, so a failure yields "hash mismatch"
   with no diff. Arrow type fidelity is exactly what marrow should assert.
4. The empirical argument: ClickHouse imported a sqllogictest runner, and its
   `tests/sqllogic/known_failures.txt` is **174,005 lines**, produced by
   `generate_known_failures.py`, whose whole job is re-blessing every failure.

**Fuzzing, metamorphic oracles, hypothesis-generated queries — deferred, not
rejected.** They need a mostly-correct baseline to be informative; on an engine
at this stage they re-find known defects and cost more in triage than they
return. Revisit once the corpus is green and stable. The techniques worth
returning to are SQLancer-style TLP (`filter(p) ∪ filter(~p) ∪
filter(p.is_null())` == unfiltered) and the BuzzHouse `QueryOracle` catalogue.

## Case layout

**Three committed files per *area*, not per case.** ClickHouse's granularity is
one `.sql` holding many queries beside one `.reference` holding their outputs;
this follows it. An area holds as many cases as it needs.

```
golden/
  test_aggregate.py         # runtime lane: query in the body, SQL twin in the docstring
  test_aggregate.mojo       # AOT lane: the same cases, same names
  test_aggregate.expected   # one expectation, read by both lanes
```

All three share the stem `test_aggregate`, so they sort adjacently in one
top-level **`golden/`** directory — the lanes are two renderings of one corpus, not two
corpora.

The SQL twin lives in the docstring, so the Python file is one artifact rather
than two — the pattern `python/marrow/tests/clickbench.py` already uses for its
43 queries:

```python
@case(fixture="basic")
def sum_by_key(t):
    """SELECT k, sum(v) AS total FROM t GROUP BY k ORDER BY k"""
    return t.aggregate(by=["k"], total=("sum", "v")).order_by("k")
```

`test_aggregate.expected` is committed **as text** so expectation changes are
reviewable in a diff — that review is the guard this design depends on, and a
binary blob would destroy it:

```
== sum_by_key
k: string, total: int64
a  9
b  6
```

The runner parses it and materialises a gitignored `.expected.arrow` cache that
the Mojo lane reads with `read_ipc_file` (`marrow/ipc.mojo:2404`) and compares
using `RecordBatch.__eq__` (`marrow/tabular.mojo:117`). Only Python parses the
text; Mojo never does — which matters, since marrow has no JSON library (Known
Limitation 1). The cache is derived, so it cannot drift from the reviewed text.

With ~10 areas that is ~30 committed files for the whole corpus, independent of
how many cases each area holds.

## Fixtures

Fixtures are **Arrow IPC files**, not construction code, so all three
renderings read the same bytes and cannot drift apart. Every case loads its
fixture into an **in-memory source**:

| lane | source |
|---|---|
| runtime (Python) | `marrow.memtable(batch)` |
| AOT (Mojo) | `in_memory_table(...)` (`marrow/expr/relations.mojo:1212`) |
| DuckDB twin | replacement scan over the pyarrow table |

The fixture set carries the edge cases by construction rather than by whoever
remembers them: nulls, all-null columns, empty groups, NaN and ±inf, integer
extremes, empty batches, unicode and empty strings, plus **sliced and chunked
variants of the same data** — the `offset`-has-two-conventions trap in
`docs/backlog.md` §0 is only reachable that way.

## Expectations come from DuckDB, never from marrow

Every case carries a SQL twin, and `--regenerate` runs it through DuckDB to
produce `expected.arrow` and `expected.txt`.

**The runner must refuse to source an expectation from marrow's own output.**
This is the single guard between a golden corpus and ClickHouse's
auto-generated 174,005-line failure list. Where DuckDB and Arrow semantics
legitimately differ (null ordering, decimal scale, integer overflow), the case
records the divergence and its reason in `case.toml`; it is reviewed like code,
never generated.

DuckDB is already a dev dependency (`pixi.toml`, `bench` environment), and
`python/marrow/tests/clickbench.py` already writes each of its 43 queries as a
marrow expression and a SQL twin — this generalizes an established pattern.

## Seeding from the SQLite corpus

The expression area is seeded **once, offline** from the neutral SQLite
sqllogictest corpus (`~/Workspace/duckdb/test/sqlite/select1-5.test_slow`) —
the one generated by cross-checking five engines, so it encodes no vendor's
semantics.

Measured against marrow's IR: **944 of 3,000 query blocks (31.5%)** are
expressible; the rest are blocked by subqueries (1,056), set ops (1,000),
`IN (...)` (952) and `EXISTS` (217). The expressible shapes are `WHERE` (232),
`WHERE+ORDER BY` (210), `WHERE+ORDER BY+CASE` (119), `WHERE+CASE` (110),
`ORDER BY` (96), bare `SELECT` (76) and `CASE` (51).

Two properties make this cheap where the DataFusion corpus was not:

- **The schema is fixed** — `t1(a, b, c, d, e INTEGER)`. One fixture, no DDL
  translation. DataFusion's 460 `CREATE EXTERNAL TABLE ... STORED AS CSV`
  statements are what made that corpus unaffordable.
- **Their expectations are not used.** This design regenerates from DuckDB, so
  the corpus's MD5 result hashing and `query IIR` type-letter coercion — the
  reasons the format is unusable as-is — are simply bypassed.

A throwaway transpiler handles SELECT-list expressions, WHERE predicates and
ORDER BY over the known schema: arithmetic, comparisons, boolean, `CASE`,
column references. It is run once and its output is committed as ordinary
golden cases. **No runner, no upstream dependency, no `known_failures.txt`.**

Two bounds on it:

- It seeds the **expression, filter and sort** areas only. Not one expressible
  query has a `GROUP BY` or an aggregate, and none has a join or meaningful
  null semantics. Everything else stays hand-written.
- **Sample it, but the bound is instantiations, not cases.** Every query in
  this corpus runs over one schema of one dtype — `t1(a, b, c, d, e INTEGER)` —
  which is the *best* case for instantiation reuse, so the seed is cheaper per
  case than the hand-written areas that deliberately vary dtypes (cast,
  temporal, decimal, string). Measure a ~20-case driver first and extrapolate
  before fixing a corpus size. The queries are mechanical variations with steep
  diminishing returns regardless, so select for expression diversity rather
  than taking all 944.

## Both lanes run every case

Per invariant 2 ("one engine, two drivers"), **the AOT and runtime lanes must
support the same query set.** Every case has both twins. A query one lane
cannot express is not an exemption — it is an invariant-2 violation, and the
corpus is where it surfaces. Windows are the known instance today (AOT-only,
backlog M2.3); the corpus will name it rather than let it stay implicit.

**Compile cost is governed by the selection and by distinct instantiations —
not by file count.** `MojoRunner.write_driver` (`conftest.py:258`) generates
**one driver per pytest selection**, content-addressed by a hash of its source,
so 150 cases across 10 files cost exactly what 150 cases in 1 file cost.
Files are an organisation choice. Two things actually drive cost:

- **Fixed:** elaborating marrow, roughly 3 minutes, paid once per selection.
  This is why all 9 `expr/tests` files together measured 4m43s / 17.0 GB while
  `test_join.mojo` alone measured 3m18s / 19.6 GB.
- **Marginal:** each distinct fused instantiation — a new comptime type
  combination. Cases sharing dtypes and shapes share instantiations.

So the levers are: **narrow the selection** to cut peak memory (run areas as
separate `pytest` invocations; concurrent ones are safe, drivers being
content-addressed), and **vary values rather than types** to cut marginal cost.

Per-case `marrow compile` binaries would cost minutes *each* and are not
viable under any arrangement.

## Execution-configuration leg

The same corpus, the same expectations, re-run with a different execution
configuration — the ClickHouse `SettingsRandomizer` and polars
`POLARS_IDEAL_MORSEL_SIZE=4` pattern, at the smallest scale that pays:

| axis | today | how |
|---|---|---|
| morsel size | `_DEFAULT_MORSEL_SIZE = 8192` (`python/marrow/expr.py`) | `--morsel-size 4` |
| worker threads | `collect(num_threads=0)` (`python/marrow/expr.py:295`) | `--num-threads 8` |
| optimizer | `optimize()` is unconditional (`marrow/expr/relations.mojo:569`) and unexposed | `--no-optimize`, needs a ~20-line binding |

These are new `pytest_addoption` entries alongside the existing
`--mojo`/`--python`/`--cpu`/`--gpu` (`conftest.py:617`), applied by
monkeypatching the defaults. The optimizer toggle is DuckDB's highest-yield
verification mode for the least code: a rewrite that changes an answer is a
bug, and pruning that drops rows is precisely the failure the M1 gate measures.

This leg is cheap on the Python side because `libmarrow.so` is prebuilt. It is
**not** cheap on the Mojo side — the AOT cases construct their contexts inline
and a re-run is a rebuild — so the configuration matrix applies to the runtime
lane only.

## Directory structure

```
golden/
  __init__.mojo          # golden/ is a Mojo package, so its modules are importable
  conftest.py            # case discovery, comparison, --regenerate
  fixtures/*.arrow       # a handful of shared datasets, incl. sliced + chunked
  test_<area>.py         # areas: aggregate, filter, project, sort, limit, join,
  test_<area>.mojo       #        cast, string, temporal, null_semantics
  test_<area>.expected
```

Four mechanics make a top-level directory work with the existing harness:

- **`testpaths = marrow python` in `pytest.ini` gains `golden`.** One line.
- **Files must be named `test_*`.** `pytest_collect_file` (`conftest.py:804`)
  collects any `test_*.mojo` under rootdir — it is not restricted to `marrow/` —
  and `python_files = test_*.py bench_*.py` governs the Python side.
- **`golden/` needs `__init__.mojo`.** `module_path` (`conftest.py:251`) turns
  `golden/test_aggregate.mojo` into `golden.test_aggregate`, and the generated
  driver imports that.
- **The Mojo cases use *absolute* `from marrow.x import ...`**, the opposite of
  the in-package rule, because they sit outside the package —
  `benchmarks/profiles/profile_join.mojo` already does exactly this.

One trade-off this buys: `mojo precompile marrow` compiles `marrow/` only, so
the golden Mojo cases fall outside the warning-clean gate. They are still
compiled by every `pytest` run that selects them.

## Risks

- **Every case is still written twice** — once in Python, once in Mojo — even
  though the file count is now per area. The Mojo twin is mechanical from the
  Python one, but it is hand-written. If the corpus ever becomes generated
  rather than hand-written, revisit: at that scale a spec IR plus one renderer
  per lane beats two hand-written artifacts.
- **API churn breaks the `test_<area>.py` / `test_<area>.mojo` files.**
  Acceptable for a hand-written corpus of hundreds of cases across ~30 files; a
  mechanical sweep. Not acceptable at thousands, which is the same trigger as
  above.
- **Expectation churn.** An early engine changes output often. Regeneration is
  one command and the diff review is the point — but a reviewer who rubber
  stamps it re-blesses bugs, which is the failure mode this design's DuckDB
  rule exists to prevent.

## Sequencing

1. Runner, case discovery, comparison, `--regenerate` against DuckDB, fixtures.
2. First corpus slice: aggregate, filter, project, sort, limit — both lanes.
   Seed the expression/filter/sort areas from the SQLite corpus (~150 cases).
3. `--morsel-size` / `--num-threads` options, plus the optimizer-toggle binding.
4. Grow the corpus; every M2/M3 item lands with its cases, so the corpus and
   the capability list stay one artifact.
