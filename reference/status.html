Status & limitations

What works, what doesn’t, and what is known to be wrong

marrow is experimental. Both Apache Arrow and Mojo are moving targets. This page lists what works and what does not, with a pointer to the source each line comes from, so it can be checked rather than taken on trust.

How correctness is measured

Two independent checks, neither of which grades marrow against itself:

  • The golden corpus — golden/, 278 query cases. Each records a SQL query, the answer generated from DuckDB, and the marrow spelling. The expectations are never regenerated from marrow. The corpus currently carries zero xfails: every case that compiles, passes.
  • Arrow archery integration — the official cross-implementation suite, run against the C++, Rust and Go implementations in both directions (pixi run -e integration integration), skipping the layouts marrow does not implement: unions, views, run-end encoding and extension types.

Known-wrong answers

WarningFloat division by zero answers the dividend

DivKernel substitutes a 1 divisor so the SIMD lane cannot trap, so 10.0 / 0.0 is 10.0 where IEEE 754 and DuckDB both say inf; -10.0 / 0.0 is -10.0, and 0.0 / 0.0 is 0.0.

No golden case pins it, which is how it survived — so it is the one known-wrong answer the corpus does not currently catch. Integer // and % by zero are unaffected and answer NULL, as SQL does.

One latent trap is worth knowing too: count(*) desugars to count(lit(1)), whose referenced-column set is empty, so anything that prunes by “what does this read” would prune every column. Column pruning handles it by never narrowing a source to zero columns.

Capability by layer

Status
Layouts bool, numeric, string/large_string, binary/large_binary, fixed_size_binary, list/large_list/fixed_size_list, struct, map, dictionary, decimal (32/64/128/256), temporal — implemented. Union, run-end-encoded and view layouts — not
Sources A lazy scan reads one Parquet file, local or at an object-store URI through OpenDAL (whose C library is installed separately), or an in-memory batch. Arrow IPC is read and written eagerly. No CSV, no JSON, and no globs, directories or hive partitions
Parquet native reader and writer, snappy/zstd/lz4, data page v1 & v2, statistics, page index. Bloom filters are implemented but off by default and unreachable from Python. No modular encryption
Optimizer 16 rules plus column pruning. No cost model, so no join reordering and no build-side selection
Execution in-memory only — no spilling anywhere, so every aggregate and join is bounded by RAM
Joins equijoins only: inner, left, right, full, semi, anti. No nested-loop, range or asof joins
GPU element-wise kernels only (arithmetic, comparison, boolean, cast, hashing), and off unless built with -D MARROW_GPU=true
UDFs none

Python-specific limits

The Python bindings are narrower than the Mojo core, and some of the gaps are CPython-binding limits rather than missing features:

  • Most aggregates are not on the eager surface. marrow.compute has any and all, but no sum / min / max / mean; those reductions live in the query layer.
  • Row groups are skipped only in an optimized plan. .optimize() pushes filters into the Parquet scan; collect() on a plan that was not optimized reads every row group.
  • == on an Array is identity, not element-wise. Use mc.equal to compare values. Dtypes, fields and schemas do compare by value.
  • Some pyarrow.compute options are missing. skip_nulls=False, multi-key sort_keys, nan_is_null=True and boundscheck=False raise NotImplementedError, and memory_pool is ignored.

Errors

There are 300+ raise Error sites and zero typed exceptions, so failures cannot yet be caught by kind.

The open work, with complexity estimates and what blocks what, is tracked in backlog.md at the repository root.
