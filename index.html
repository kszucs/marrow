The PyArrow API you already know. Kernels run the moment you call them.

import marrow as ma

batch = ma.record_batch({
    "region": ma.array(["east", "west", "east"]),
    "price":  ma.array([10, 20, 30]),
})

hot = ma.compute.greater(batch.column("price"), ma.array([15, 15, 15]))
ma.compute.filter(batch.column("price"), hot)

Describe the whole query first; nothing executes until collect(), so the optimizer sees all of it at once.

import marrow as ma
from marrow import col, lit

ma.read_parquet("orders.parquet") \
  .filter(col("price") > lit(15)) \
  .aggregate(by=["region"], total=("sum", "price")) \
  .order_by(("total", "descending")) \
  .head(10) \
  .collect()

The dtypes are fixed at compile time, so the whole expression fuses into one SIMD loop and the linker deletes every kernel the query cannot reach.

from marrow.dtypes import field, int64
from marrow.expr import QueryCli, col, scan
from marrow.schema import schema

def main() raises:
    var cli = QueryCli("orders")
    var min_price = cli.param("min-price", int64, default=Int64(15))
    cli.argument("src")
    if cli.parse():
        var sch = schema([field("region", int64), field("price", int64)])
        cli.run(
            scan(cli.get("src"), sch^).filter(col("price", int64) > min_price)
        )
$ marrow compile query.mojo -o orders
$ ./orders orders.parquet --min-price 15    # 2.9 MB, no Python anywhere

Where it fits

How marrow relates to what you already use

marrow is alpha and far less complete than any of these. It is worth your attention where the third column is.

What it is Why you’d reach for marrow instead
PyArrow the reference Arrow implementation Same data model, same method names, zero-copy both ways. marrow runs the compute in Mojo instead of through the interpreter
Polars / DuckDB mature engines, far more complete They ship a runtime alongside your query. marrow can freeze the query itself into a binary you can drop on a machine with nothing installed
arrow-rs / DataFusion the closest architectural analogue marrow is checked against them for conformance, and adds a compile-time-fused expression lane Rust monomorphization can’t quite reach
Mojo / MAX the language and its AI runtime marrow makes Arrow first-class in Mojo, and lets one kernel source serve both CPU SIMD and GPU
Note

How correctness is checked. 278 golden query cases whose expected answers are generated from DuckDB, never from marrow, plus the official Arrow archery suite run against the C++, Rust and Go implementations in both directions. See Status & limitations for what is missing and what is known to be wrong.

See it run

Sixty seconds with marrow

Build arrays straight from Python data — the type is inferred in one pass, and None marks a null:

ages   = ma.array([25, 35, 45, None, 55])
names  = ma.array(["Alice", "Bob", "Carol", "Dave", "Eve"])
salary = ma.array([70_000, 90_000, 110_000, 50_000, 130_000])

print(ages)
print(names)
PrimitiveArray[int64]([25, 35, 45, NULL, 55])
StringArray([Alice, Bob, Carol, Dave, Eve])

Compute is vectorized and null-aware — a null in either operand propagates:

print("next year:", ma.compute.add(ages, ma.array([1] * 5)))
print("over 40:  ", ma.compute.greater(ages, ma.array([40] * 5)))
next year: PrimitiveArray[int64]([26, 36, 46, NULL, 56])
over 40:   BoolArray([False, False, True, NULL, True])

Assemble columns into a RecordBatch, then query it lazily:

people = ma.record_batch({"age": ages, "name": names, "salary": salary})

(ma.memtable(people)
   .filter(col("salary") > lit(60_000))
   .aggregate(headcount=("count", "salary"), payroll=("sum", "salary"))
   .collect()
   .to_pylist())
[{'headcount': 4, 'payroll': 400000}]

Every array speaks the Arrow C Data Interface, so it crosses into the rest of the ecosystem as a pointer exchange:

import pyarrow as pa
pa_ages = pa.array(ages)          # marrow → PyArrow, no copy
back    = ma.array(pa_ages)       # PyArrow → marrow, no copy
print(pa_ages.type, "|", len(back))
int64 | 5
